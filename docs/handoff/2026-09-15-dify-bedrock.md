# Dify + Amazon Bedrock Integration Handoff

Date: 2026-09-15

## 1. Goal

Integrate Dify into the existing `datacenter-project` AWS environment as an Incident Analysis Workflow Orchestrator.

Target flow:

```text
Simulator
→ FastAPI
→ ML Anomaly Detection
→ Incident Manager
→ Dify Workflow
→ Amazon Bedrock
→ Incident Analysis Result
```

Dify does not perform anomaly detection itself.
ML detects anomalies, while Dify orchestrates the LLM-based incident analysis.

## 6. Code Node

Input:

```text
incident_context
```

The Code node parses the JSON and calculates a temporary severity.

Current temporary rules:

```text
anomaly_rate >= 0.30 → CRITICAL
anomaly_rate >= 0.15 → HIGH
anomaly_count > 0    → MEDIUM
otherwise            → LOW
```

These thresholds are only for the first Workflow validation.
They are not intended to represent final production incident policy.

Outputs:

```text
severity
anomaly_count
anomaly_rate
parsed_context
```

The Code node was tested successfully.

## 9. IAM Design

A dedicated IAM Role was created:

```text
datacenter-dify-bedrock-role
```

Trusted service:

```text
ec2.amazonaws.com
```

Purpose:

```text
Allow the datacenter-dify EC2 instance to invoke Amazon Bedrock Nova Pro
through the approved APAC inference profile for the Dify Incident Analysis workflow.
```

The Bedrock permissions were intentionally designed with least privilege instead of using broad policies such as `AmazonBedrockFullAccess`.

The policy is intended to:

- allow model / inference-profile discovery
- allow inference only for Nova Pro
- use the approved APAC inference profile
- avoid broad Bedrock administrative permissions

Do not commit real AWS Account IDs, credentials, access keys, secret keys, administrator emails, or passwords to GitHub.
